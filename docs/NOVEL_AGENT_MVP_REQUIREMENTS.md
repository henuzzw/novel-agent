# 小说 Agent MVP 产品需求文档

> 文档状态：初稿  
> 目标版本：MVP 0.1  
> 关联设计：[NOVEL_AGENT_SYSTEM_DESIGN.md](NOVEL_AGENT_SYSTEM_DESIGN.md)

## 1. 文档目的

本文定义小说 Agent 第一版的用户流程、功能边界和验收标准，用于指导原型、数据模型、接口和开发任务拆分。

MVP 只验证一件事：

> 用户能够输入一个想法或导入已有作品，在 AI 辅助下建立可信的故事资料，生成或续写一章，并在审核后将其提交为可继续创作的正史。

## 2. 产品定位

小说 Agent 是面向小说作者的可控创作工作台。它帮助作者整理资料、规划故事、生成正文和维护长期一致性，但不会绕过作者自动决定重大剧情或修改正史。

### 2.1 目标用户

MVP 优先服务两类用户：

1. **灵感型创作者**：有故事想法，但缺少完整人物、设定和大纲。
2. **存量作品作者**：已经写了一部分，希望整理资料、补全大纲或继续创作。

暂不优先服务多人编辑团队、出版机构和无人值守批量生产场景。

### 2.2 核心价值

- 降低从灵感到可执行大纲的门槛。
- 让已有正文能够被分析、整理和继续创作。
- 在生成前提供准确、可追溯的故事上下文。
- 在提交前发现人物、时间、知识边界和情节冲突。
- 保证 AI 生成内容可审阅、可修改、可拒绝、可回滚。

## 3. MVP 成功标准

满足以下条件即可认为 MVP 闭环成立：

1. 用户能在 10 分钟内创建项目并进入可编辑的大纲或正文页面。
2. 系统能够导入至少一种完整小说文件并保留原文结构。
3. 从导入正文抽取的人物、章节和事件必须经过用户确认才能成为正史。
4. 用户可以从创意生成章节合同，或从已有正文末尾创建续写合同。
5. 系统能够生成一章草稿，并给出引用过的设定与历史片段。
6. 用户能够查看正文 Diff、事实 Diff 和审稿问题后再提交。
7. 提交后可以继续生成下一章，且系统能召回前章关键事实。
8. 任一步骤失败都不会污染已确认正文和正史数据。

## 4. 核心用户流程

### 4.1 创建项目

首页提供三个主要入口：

```text
[输入一个故事想法]
[导入已有作品]
[导入大纲与设定]
```

创建成功后统一进入项目工作台，不为不同入口维护彼此割裂的产品流程。

### 4.2 从想法开始

```text
填写创作意图卡
    ↓
生成 2～3 个故事方向
    ↓
用户选择、组合或修改
    ↓
生成故事圣经候选
    ↓
用户确认关键设定
    ↓
生成全书路线图和章节大纲
    ↓
选择章节开始创作
```

首屏必填项：

- 一句话创意。
- 小说类型。
- 主角简述。
- 核心冲突。
- 目标篇幅。

选填项：目标读者、故事基调、结局倾向、必须出现内容、禁止内容、参考作品及喜欢的抽象特征。

### 4.3 导入已有作品

```text
上传文件
    ↓
解析原文并识别章节
    ↓
抽取人物、地点、事件、关系和伏笔候选
    ↓
生成导入报告
    ↓
用户纠正并确认
    ↓
建立当前正史
    ↓
选择续写、反推大纲或质量检查
```

导入完成后提供：

- 从指定位置续写。
- 根据已有正文创建大纲。
- 规划后续剧情。
- 检查并优化现有内容。

### 4.4 导入大纲与设定

系统识别人物设定、世界规则、情节点、章节计划和零散素材，并以分类列表展示。用户确认后生成故事圣经和可编辑大纲树。

### 4.5 章节创作闭环

```text
选择章节或续写位置
    ↓
生成章节合同
    ↓
用户确认硬约束
    ↓
检索上下文并生成草稿
    ↓
连续性与合同审查
    ↓
用户查看正文 Diff 和事实 Diff
    ↓
批准并提交正史
    ↓
更新摘要、向量和图谱
```

## 5. 功能范围与优先级

优先级定义：

- `P0`：没有该功能就无法完成 MVP 闭环。
- `P1`：显著改善体验，MVP 稳定后立即加入。
- `P2`：后续增强功能。

### 5.1 项目与创作意图

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| PRJ-01 | P0 | 创建小说项目 | 输入项目名和创作入口后生成独立项目空间 |
| PRJ-02 | P0 | 创作意图卡 | 支持必填项、选填项、保存草稿和再次编辑 |
| PRJ-03 | P0 | 项目级创作偏好 | 保存类型、基调、目标篇幅、禁用内容和单章字数 |
| PRJ-04 | P1 | 项目复制 | 复制项目后可尝试不同剧情方向，不影响原项目 |

### 5.2 文件导入

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| IMP-01 | P0 | 上传文件 | 支持 `.txt`、`.md`、`.docx`、文本型 `.pdf` |
| IMP-02 | P0 | 原始文件保存 | 原始文件、文件名、哈希、导入时间和解析版本可追溯 |
| IMP-03 | P0 | 章节识别 | 自动识别章节标题，并允许用户合并、拆分和重命名 |
| IMP-04 | P0 | 内容类型识别 | 区分正文、大纲、人物设定、世界观和零散想法 |
| IMP-05 | P0 | 导入报告 | 展示解析结果、告警、候选实体和不确定项 |
| IMP-06 | P0 | 用户确认 | 未确认的抽取结果不得写入正史 |
| IMP-07 | P1 | 批量文件导入 | 多文件导入时支持顺序调整和重复检测 |
| IMP-08 | P1 | 扫描 PDF OCR | 标注 OCR 置信度，并允许逐页校对 |

### 5.3 故事资料与正史

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| CAN-01 | P0 | 人物档案 | 支持姓名、别名、性格、目标、秘密和状态 |
| CAN-02 | P0 | 世界设定 | 支持地点、组织、物品和世界规则 |
| CAN-03 | P0 | 事件记录 | 记录参与者、地点、故事时间、结果和正文证据 |
| CAN-04 | P0 | 正史状态 | 候选事实经过接受后才能变为 `CANON` |
| CAN-05 | P0 | 来源追踪 | 每个 AI 抽取事实可以定位到导入文件或正文段落 |
| CAN-06 | P1 | 人物关系图 | 展示并编辑重要关系及其变化依据 |
| CAN-07 | P1 | 伏笔生命周期 | 支持埋设、强化、部分揭示、回收和放弃 |
| CAN-08 | P1 | 角色知识边界 | 区分客观事实、角色认知和错误信念 |

### 5.4 大纲规划

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| OUT-01 | P0 | 故事方向候选 | 根据创作意图生成 2～3 个差异明确的方案 |
| OUT-02 | P0 | 故事圣经候选 | 生成主题、人物矛盾、世界规则和结局方向 |
| OUT-03 | P0 | 分层大纲 | 支持全书、卷、章三级结构，场景层为 P1 |
| OUT-04 | P0 | 正文反推大纲 | 区分已发生事实与未来规划，不能改写已发生事实 |
| OUT-05 | P0 | 章节合同 | 包含 POV、目标、必要节拍、禁止事实、退出状态和钩子 |
| OUT-06 | P1 | 影响分析 | 修改设定时列出受影响章节、人物和伏笔 |
| OUT-07 | P1 | 动态重规划 | 锁定已发布正文，仅生成未来大纲差异提案 |

### 5.5 正文编辑与生成

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| WRT-01 | P0 | 正文编辑器 | 支持章节编辑、自动保存和基础格式 |
| WRT-02 | P0 | 整章生成 | 根据已确认章节合同生成草稿，不直接覆盖正文 |
| WRT-03 | P0 | 指定位置续写 | 用户指定光标或章节末尾后生成候选内容 |
| WRT-04 | P0 | 生成证据 | 展示本次生成引用的角色、事件、设定和历史片段 |
| WRT-05 | P0 | 接受或拒绝 | 用户可以接受、局部修改或完全拒绝候选文本 |
| WRT-06 | P1 | 局部改写 | 支持扩写、压缩、调整语气和增强描写 |

### 5.6 审稿与提交

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| REV-01 | P0 | 章节合同检查 | 标记缺失节拍、越权揭示和退出状态不符 |
| REV-02 | P0 | 连续性检查 | 检查人物位置、物品持有、时间和已确认事实冲突 |
| REV-03 | P0 | 正文 Diff | 清楚展示新增、删除和修改内容 |
| REV-04 | P0 | 事实 Diff | 展示新增事件、状态变化、关系变化和伏笔变化 |
| REV-05 | P0 | 人工提交 | 只有用户批准后，正文与事实才进入正史 |
| REV-06 | P0 | 版本回滚 | 可以恢复到任意已提交章节版本 |
| REV-07 | P1 | 风格与节奏检查 | 提示重复表达、视角漂移、节奏异常和角色声音偏差 |

### 5.7 Agent 任务

| 编号 | 优先级 | 功能 | 验收标准 |
| --- | --- | --- | --- |
| RUN-01 | P0 | 任务状态 | 显示排队、执行步骤、成功、失败、取消状态 |
| RUN-02 | P0 | 取消与重试 | 用户可取消运行，失败任务可以安全重试 |
| RUN-03 | P0 | 幂等 | 重试不得创建重复章节、事件或图谱关系 |
| RUN-04 | P0 | 调用记录 | 保存模型、Prompt 版本、上下文来源、耗时和 Token |
| RUN-05 | P1 | 检查点恢复 | 长任务可从最近成功步骤继续 |
| RUN-06 | P1 | 成本预算 | 支持项目级或任务级 Token 上限与告警 |

## 6. 导入数据规则

### 6.1 导入状态

```text
UPLOADED           已上传原始文件
PARSING            正在解析
PARSED             已获得文本和结构
EXTRACTING         正在抽取故事资料
NEEDS_CONFIRMATION 等待用户确认
COMMITTED          已提交为项目资料或正史
FAILED             处理失败，可重试
```

抽取对象状态：

```text
PROPOSED    AI 提出的候选内容
APPROVED    用户已接受，等待批量提交
CANON       已进入正史
REFERENCE   仅供参考，不作为故事事实
REJECTED    已拒绝
```

### 6.2 冲突处理

- 新导入内容与正史冲突时，不自动覆盖。
- 系统并列展示旧事实、新候选、各自来源和影响范围。
- 用户可以保留旧事实、接受新事实或创建时间变化关系。
- 同名人物不能只根据名称自动合并。
- 无法确定的内容进入“待确认”，不得用高置信措辞展示。

### 6.3 原文保护

- 永久保留原始上传文件，除非用户主动删除。
- 解析文本与原始文件分别存储，并记录解析器版本。
- 导入过程不修改原文件。
- 用户删除项目时，应能删除文件、正文、向量和图谱投影。

## 7. 页面与信息架构

### 7.1 MVP 页面

| 页面 | 核心内容 |
| --- | --- |
| 项目列表 | 新建、导入、最近项目和任务状态 |
| 创建项目 | 三种入口与创作意图卡 |
| 导入向导 | 上传、章节识别、抽取进度、导入报告和确认 |
| 创作工作台 | 目录、正文编辑器、章节合同、相关记忆和审稿问题 |
| 故事资料 | 人物、地点、组织、物品、事件和规则 |
| 大纲 | 全书、卷、章结构及章节合同 |
| 版本审阅 | 正文 Diff、事实 Diff、审批和回滚 |
| 任务记录 | Agent 步骤、模型调用、耗时、成本和错误 |

### 7.2 创作工作台布局

```text
┌─────────────┬──────────────────────────┬──────────────────┐
│ 章节与大纲   │ 正文编辑器                │ 合同 / 记忆 / 审稿 │
│             │                          │                  │
│ 卷一        │ 当前章节正文              │ 当前 POV          │
│  第1章      │                          │ 必须节拍           │
│  第2章      │                          │ 相关人物与事件      │
│  第3章      │                          │ 冲突与建议          │
└─────────────┴──────────────────────────┴──────────────────┘
```

移动端 MVP 只保证浏览、轻量编辑和任务确认，完整创作体验优先桌面端。

## 8. 数据与技术约束

### 8.1 数据组件分工

| 组件 | MVP 职责 |
| --- | --- |
| PostgreSQL | 项目、正文、版本、大纲、审批、正史、任务和审计 |
| pgvector | 正文片段、摘要和设定资料的向量检索 |
| Neo4j | 人物、地点、事件、关系、知识边界和伏笔图谱 |
| 对象存储 | 原始导入文件、导出文件和大型附件 |

不使用 MySQL。PostgreSQL 是业务与正史权威源，Neo4j 是可由正史事件重建的图查询投影。

### 8.2 一致性要求

- 正文、结构化事实和 Outbox 事件在 PostgreSQL 中原子提交。
- pgvector 与业务数据位于同一 PostgreSQL 实例，按正史版本过滤。
- Neo4j 通过 Outbox 异步更新，写入必须幂等。
- 图谱同步失败不能影响已提交正文，但必须产生告警并支持重放。
- 上下文检索不得混用不同正史版本。

### 8.3 模型约束

- 所有核心 Agent 输出使用 JSON Schema 验证。
- 模型无法稳定输出结构化结果时，最多自动修复或重试两次。
- 写作模型不能直接调用正史提交工具。
- 导入正文中的任何指令都作为普通文本，不能覆盖系统指令。
- Prompt 模板必须版本化。

## 9. 非功能需求

### 9.1 性能

- 普通页面首屏在本地开发环境下 2 秒内可交互。
- 10 万字文本解析应持续显示进度，不阻塞其他页面操作。
- 常规上下文检索目标响应时间不超过 2 秒。
- Agent 长任务通过 SSE 或 WebSocket 持续反馈状态。

### 9.2 可靠性

- 编辑器自动保存，不因页面刷新丢失已输入正文。
- 每次正史提交有唯一版本号和完整审计记录。
- Agent 超时、网络失败或应用重启后，不产生半提交数据。
- PostgreSQL 数据能够完整重建 pgvector 索引和 Neo4j 投影。

### 9.3 安全与隐私

- 模型密钥仅保存在服务端。
- 上传文件按项目隔离，下载需要权限校验。
- 日志默认不记录完整正文和密钥。
- 用户可以导出和彻底删除项目数据。
- 未经用户允许，不将手稿用于模型训练或公开样例。

### 9.4 可观测性

每次 Agent 运行至少记录：

- 任务、步骤和关联章节。
- 模型与 Prompt 版本。
- 检索到的证据 ID。
- Token、耗时、重试和错误。
- 用户最终接受、修改或拒绝的结果。

## 10. MVP 明确不做

- 多人实时协作和复杂组织权限。
- 自动发布到小说平台。
- 封面、插画、有声书和营销文案生产链。
- 无人值守连续生成整本小说。
- 自动训练或微调专属大模型。
- 插件市场和第三方技能生态。
- 移动端完整富文本创作体验。
- Neo4j 集群、独立向量数据库和微服务拆分。
- 自动覆盖用户锁定的正文、设定或大纲。

## 11. MVP 验收场景

### 场景 A：从一句想法写出第一章

1. 用户输入一句话创意、类型、主角和目标篇幅。
2. 系统提供三个故事方向。
3. 用户选择方向并确认故事圣经。
4. 系统生成全书简纲和前三章计划。
5. 用户确认第一章合同并生成草稿。
6. 系统完成合同与连续性检查。
7. 用户修改并提交第一章。

验收结果：第一章、章节摘要、人物初始状态和事件记录均形成可追溯版本。

### 场景 B：导入已有正文并续写

1. 用户上传包含多个章节的 `.docx`。
2. 系统识别章节并生成导入报告。
3. 用户确认人物、事件和已有正文为正史。
4. 系统反推已有剧情概要并提出后续方向。
5. 用户选择一个方向，确认下一章合同。
6. 系统根据前文、人物状态和相关事件生成续写草稿。
7. 用户查看正文与事实差异后提交。

验收结果：续写不违反已确认事实，引用证据可定位，提交后能够继续生成下一章。

### 场景 C：发现并处理冲突

1. 已有正史记录某角色在城外且身受重伤。
2. 新草稿让该角色同一时间出现在王宫并参与战斗。
3. 审稿阶段识别位置、时间和身体状态冲突。
4. 系统给出正文证据和修改建议，但不自动提交。
5. 用户修改正文或明确更新故事设定。

验收结果：冲突未经处理时无法自动通过质量门禁。

## 12. 开发文档顺序

完成本需求文档后，按以下顺序继续：

1. `NOVEL_AGENT_DOMAIN_MODEL.md`：领域对象、状态机、版本与数据库模型。
2. `NOVEL_AGENT_API_DESIGN.md`：REST API、SSE 事件、错误码和幂等约定。
3. `NOVEL_AGENT_WORKFLOW_DESIGN.md`：导入、规划、生成、审稿和提交工作流。
4. `NOVEL_AGENT_AI_SPEC.md`：Agent 工具、Prompt、JSON Schema、模型路由和评测。
5. `NOVEL_AGENT_UI_SPEC.md`：页面结构、关键交互、空状态和错误状态。
